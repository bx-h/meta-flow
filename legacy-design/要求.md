请在当前仓库中实现一个名为 meta-flow 的 Codex 工作流。

meta-flow 的目标：
把用户模糊需求转化为可澄清、可提案、可评审、可裁决、可拆解、可执行、可验收、可重新调整目标的完整工作流。

重要：
这不是简单的多 agent demo。
这是一套面向模糊任务落地的控制流框架。
请严格保留以下角色，不要随意合并：

方案提出阶段：
1. questioner / 提问者
2. researcher_proposer / 调研与提案者
3. reviewers / 多个评审者
4. adjudicator / 裁决者
5. proposal_summarizer / 提案摘要者
6. user_confirmation / 用户确认 gate，不是 agent

执行阶段：
7. planner / 规划者
8. direction_evaluator / 方向评估者
9. task_decomposer / 任务拆解者
10. executor / 具体任务执行者
11. result_verifier / 具体任务结果验收者
12. final_summarizer / 最终摘要者
13. user_final_confirmation / 用户最终确认 gate，不是 agent

不要把 executor 和 verifier 设计成执行/验收整个 milestone。
正确粒度是：
- planner 负责拆 milestone。
- task_decomposer 把当前 milestone 拆成更小的 concrete tasks。
- executor 每次只执行一个 concrete task。
- result_verifier 每次只验收一个 concrete task。
- milestone 是多个 concrete task 全部通过后的阶段检查点。

不要把裁决者简化成脚本。
脚本可以做机械聚合，但裁决者必须根据 reviewer 反馈、用户反馈、风险、阻塞点决定下一步路由。

不要省略 direction_evaluator。
它负责在每个 milestone 完成后，或者执行过程中出现新发现后，判断：
- 当前方向是否仍然准确。
- 原目标是否需要调整。
- 是否出现了会改变方案的新事实。
- 是否需要回到方案提出阶段。
- 是否需要重新询问用户。
- 是否应继续执行下一个 milestone。

默认不引入 LangGraph、CrewAI、AutoGen 等重依赖。

- Skill
- 自定义 subagents
- 状态文件

- 标准库 Python 校验脚本
- 示例任务目录
- 文档

========================
一、核心状态机
========================

meta-flow 分为两个大阶段：

A. 方案提出阶段

INTAKE
  -> QUESTIONING
  -> GOAL_CONTRACT_DRAFTED
  -> RESEARCH_AND_PROPOSAL
  -> PROPOSAL_REVIEW
  -> ADJUDICATION
  -> PROPOSAL_REWORK
  -> PROPOSAL_SUMMARY
  -> USER_PROPOSAL_CONFIRMATION
  -> PROPOSAL_ACCEPTED

B. 执行阶段

PLANNING
  -> USER_PLAN_CONFIRMATION
  -> MILESTONE_SELECTED
  -> TASK_DECOMPOSITION
  -> TASK_EXECUTION
  -> TASK_VERIFICATION
  -> TASK_REPAIR
  -> MILESTONE_COMPLETED
  -> DIRECTION_EVALUATION
  -> CONTINUE_NEXT_MILESTONE
  -> REPLAN
  -> GOAL_ADJUSTMENT_REQUIRED
  -> FINAL_SUMMARY
  -> USER_FINAL_CONFIRMATION
  -> DONE

允许的关键回环：

1. 方案 review 不通过：
PROPOSAL_REVIEW -> ADJUDICATION -> PROPOSAL_REWORK -> PROPOSAL_REVIEW

2. 用户不认可提案：
USER_PROPOSAL_CONFIRMATION -> ADJUDICATION -> QUESTIONING 或 RESEARCH_AND_PROPOSAL

3. 具体任务验收失败：
TASK_VERIFICATION -> TASK_REPAIR -> TASK_EXECUTION -> TASK_VERIFICATION

4. milestone 后发现方向偏移：
DIRECTION_EVALUATION -> GOAL_ADJUSTMENT_REQUIRED -> QUESTIONING 或 RESEARCH_AND_PROPOSAL

5. milestone 后发现只是计划有问题：
DIRECTION_EVALUATION -> REPLAN -> PLANNING 或 TASK_DECOMPOSITION

必须设置停止条件：
- proposal review/rework 最多 3 轮。
- 单个 concrete task repair 最多 2 轮。
- direction adjustment 最多 2 轮。
- 超过上限后，必须生成 blocked report，请求用户决策。

========================
三、Agent 职责
========================

1. questioner / 提问者

文件：.codex/agents/questioner.toml

职责：
- 面对模糊需求，补全问题细节，细化问题边界。
- 输出 questioning-report.json 和 goal-contract.json。
- 最多提出 5 个高价值问题。
- 不允许问低价值问题。
- 如果缺失信息不阻塞，则写入 assumptions，而不是无限追问。
- 不写代码，不做执行方案，不做技术选型。

必须区分：
- blocking question：不问就无法继续。
- non-blocking uncertainty：可通过 assumption 继续。

2. researcher_proposer / 调研与提案者

文件：.codex/agents/researcher-proposer.toml

职责：
- 基于 goal-contract 做调研、搜索、读代码、读文档。
- 输出 proposal.md。
- 给出主方案、备选方案、取舍理由、风险、验收方式。
- 不写代码。
- 不擅自改变 goal-contract。
- 如发现 goal-contract 有问题，只能记录为 issue，交给 adjudicator 或 direction_evaluator。

3. reviewers / 多评审者

文件：
- product-reviewer.toml
- technical-reviewer.toml
- risk-reviewer.toml
- verification-reviewer.toml

共同规则：
- 每个 reviewer 输出 reviewer-report.json。
- reviewer 之间可以读取彼此意见，避免重复提出同一问题。
- reviewer 不修改 proposal。
- reviewer 不裁决最终路线。
- reviewer 只给 pass / revise / block 和证据。

product-reviewer：
- 判断 proposal 是否真正解决用户目标。
- 关注用户价值、目标边界、非目标、需求偏差。

technical-reviewer：
- 判断技术可行性、复杂度、依赖影响、架构影响。
- 关注实现路径是否过度复杂或不可维护。

risk-reviewer：
- 判断安全、数据、权限、破坏性操作、回滚风险。
- 高风险但没有缓解方案时必须 block。

verification-reviewer：
- 判断 acceptance criteria 是否可测。
- 如果验收标准不可执行、不可观察、不可复现，必须 revise 或 block。

4. adjudicator / 裁决者

文件：.codex/agents/adjudicator.toml

职责：
- 接收 reviewer reports、review aggregate、用户反馈、direction evaluator 输出。
- 去重、合并、裁决。
- 处理 reviewer 冲突。
- 决定下一步 route。

裁决规则：
- 任一 reviewer block，不等于自动终止；adjudicator 必须判断 block 是否合理。
- 如果 block 合理，进入 ask_user、adjust_goal 或 block。
- 如果只有 revise，生成明确 rework instructions，回到 researcher_proposer。
- 如果全部 pass，进入 proposal_summarizer。
- 如果用户不认可 proposal，adjudicator 判断原因：
  - 目标不清：回到 questioner。
  - 方案不足：回到 researcher_proposer。
  - 验收标准错误：回到 verification-reviewer 或 questioner。
  - 目标变化：生成 goal-contract patch，并请求用户确认。
- adjudicator 不写代码。
- adjudicator 不直接修改 proposal，只写 adjudication-report.json。

5. proposal_summarizer / 提案摘要者

文件：.codex/agents/proposal-summarizer.toml

职责：
- 将 proposal、review 结论、adjudicator 决策压缩成用户可确认的摘要。
- 输出 proposal-summary.md。
- 摘要必须包含：
  - 要做什么
  - 不做什么
  - 为什么这么做
  - 主要风险
  - 用户需要确认什么
- 不增加新信息。
- 不修改方案。

6. planner / 规划者

文件：.codex/agents/planner.toml

职责：
- 在用户确认 proposal 后，将 proposal 拆成 milestone-plan.json。
- milestone 是阶段性目标，不是具体执行任务。
- 每个 milestone 必须可验收、可回滚、范围清晰。
- planner 不写代码。
- planner 不把 milestone 直接交给 executor。
- planner 的输出必须交给 task_decomposer。

7. task_decomposer / 任务拆解者

文件：.codex/agents/task-decomposer.toml

职责：
- 针对当前 milestone 生成 task-list.json。
- 每个 concrete task 必须小到可以由 executor 独立完成、由 verifier 独立验收。
- 每个 concrete task 必须有：
  - objective
  - allowed_files
  - forbidden_files
  - expected_outputs
  - acceptance_checks
  - dependencies
- 不写代码。
- 不验收。
- 不调整目标。

8. executor / 具体任务执行者

文件：.codex/agents/executor.toml

职责：
- 每次只执行一个 concrete task。
- 不执行整个 milestone。
- 只能修改 task-spec 允许的文件。
- 做最小必要改动。
- 每次执行后输出 task-execution-report.json。
- 如果发现 task-spec 明显错误，不擅自扩大范围；标记 blocked 或 discovered_facts。
- 不负责最终验收。
- 不修改 goal-contract。
- 不修改 milestone-plan，除非明确被 planner/adjudicator 指示。

9. result_verifier / 具体任务结果验收者

文件：.codex/agents/result-verifier.toml

职责：
- 每次只验收一个 concrete task。
- 对照 task-spec.acceptance_checks 验收。
- 可以运行测试、lint、typecheck、脚本、diff review。
- 输出 task-verification-report.json。
- 不实现功能。
- 不替 executor 修代码。
- 如果失败，给出 minimal_repair_instructions。
- 如果发现新事实可能影响 milestone 或目标，设置 should_trigger_direction_evaluation = true。

10. direction_evaluator / 方向评估者

文件：.codex/agents/direction-evaluator.toml

职责：
- 在每个 milestone 完成后运行。
- 当 verifier 发现重大新事实时也运行。
- 判断当前执行方向是否仍然准确。
- 判断是否需要调整目标、重新规划、回到方案阶段或询问用户。
- 输出 direction-evaluation.json。
- 不写代码。
- 不直接修改 goal-contract。
- 如果需要改目标，只能生成 contract_patch，并要求用户确认。

判断标准：
- 原始目标是否仍然成立。
- proposal 的核心假设是否被推翻。
- milestone 执行结果是否暴露新边界。
- acceptance criteria 是否仍然合理。
- 是否出现用户必须决策的新问题。
- 继续执行是否可能产生错误结果或浪费成本。

11. final_summarizer / 最终摘要者

文件：.codex/agents/final-summarizer.toml

职责：
- 汇总所有 milestone、task、verification、direction evaluation。
- 输出 final-report.md。
- 面向用户说明：
  - 完成了什么
  - 未完成什么
  - 证据是什么
  - 风险和后续建议
  - 是否满足原 acceptance criteria
- 不粉饰失败。
- 不隐藏 blocked 状态。

========================
四、Skill 行为
========================

在 .agents/skills/meta-flow/SKILL.md 中写入完整 workflow 说明。

SKILL.md 必须包含 YAML frontmatter：

---
name: meta-flow
description: Use this workflow for vague, multi-step, high-reliability tasks that need questioning, proposal, review, adjudication, planning, task-level execution, verification, direction evaluation, and user confirmation before completion.
---

触发条件：
- 用户需求模糊。
- 任务跨多个文件、模块、阶段。
- 用户要求先出方案再执行。
- 用户要求高可靠落地。
- 任务执行中可能出现新发现，需要调整目标。
- 需要 milestone、子任务、验收闭环。

不触发条件：
- 用户只要一个直接回答。
- 用户只要解释代码。
- 用户明确指定一个很小的改动。
- 任务没有可执行结果。
- 任务没有可观察验收标准。

流程要求：

方案提出阶段：
1. 创建 task directory。
2. 保存 raw-request.md。
3. 调用 questioner。
4. 如果 questioner 判断存在 blocking questions，先询问用户。
5. 生成 goal-contract.json。
6. 调用 researcher_proposer 生成 proposal.md。
7. 并行调用四类 reviewer。
8. 运行 aggregate_reviews.py 做机械聚合。
9. 调用 adjudicator 进行裁决。
10. 如果 adjudicator 输出 revise_proposal，回到 researcher_proposer。
11. 如果 adjudicator 输出 ask_user，向用户提问。
12. 如果 adjudicator 输出 accept，调用 proposal_summarizer。
13. 将 proposal-summary.md 给用户确认。
14. 用户确认后进入执行阶段。

执行阶段：
1. 调用 planner 生成 milestone-plan.json。
2. 让用户确认 milestone-plan。
3. 选择当前 milestone。
4. 调用 task_decomposer 生成 task-list.json。
5. 按 dependency 顺序处理 concrete task。
6. 每个 concrete task：
   a. 调用 executor 执行。
   b. 调用 result_verifier 验收。
   c. 如果 verifier revise，回到 executor repair，最多 2 次。
   d. 如果 verifier block，停止当前 milestone，交给 adjudicator 或用户。
7. 当前 milestone 所有 concrete tasks pass 后，调用 direction_evaluator。
8. direction_evaluator 输出 continue，则进入下一个 milestone。
9. direction_evaluator 输出 replan，则回到 planner 或 task_decomposer。
10. direction_evaluator 输出 adjust_goal，则生成 contract patch，请用户确认后回到方案提出阶段。
11. 所有 milestone 完成后，调用 final_summarizer。
12. 给用户 final-report.md，请用户最终确认。
13. 用户确认后标记 DONE。

========================
五、脚本要求
========================

所有 Python 脚本尽量只用标准库。
所有脚本必须支持 --help。
所有 JSON 输出必须 pretty-print。
所有脚本遇到 schema 错误必须返回非 0 exit code。

实现以下脚本：

1. new_task.py

功能：
- 输入 raw request。
- 创建 task id。
- 创建 .meta-flow/tasks/<task-id>/。
- 初始化 state.json。
- 保存 raw-request.md。
- 打印 task directory。

2. validate_goal_contract.py

功能：
- 校验 goal-contract.json。
- 必须检查：
  - refined_goal 非空。
  - acceptance_criteria 非空。
  - verification_method 合法。
  - non_goals 存在。
  - constraints 存在。
  - risk_level 合法。

3. aggregate_reviews.py

功能：
- 读取 reviews/*.json。
- 校验 reviewer report。
- 输出 review-aggregate.json。

机械聚合规则：
- 任一 block => mechanical_result = block。
- 无 block 但有 revise => mechanical_result = revise。
- 全 pass => mechanical_result = pass。

注意：
aggregate_reviews.py 不做最终裁决。
最终裁决由 adjudicator 完成。

4. validate_adjudication.py

功能：
- 校验 adjudication-report.json。
- decision 必须属于：
  - accept
  - revise_proposal
  - ask_user
  - adjust_goal
  - replan
  - block
- next_phase 必须和 decision 一致。

5. validate_milestone_plan.py

功能：
- 校验 milestone-plan.json。
- 每个 milestone 必须有 objective、scope、acceptance_checks、risk、status。
- 如果单个 milestone scope 超过 7 项，输出 warning。

6. validate_task_list.py

功能：
- 校验 task-list.json。
- 每个 concrete task 必须有 objective、expected_outputs、acceptance_checks、dependencies、status。
- 每个 concrete task 必须足够小。
- 如果 allowed_files 为空，输出 warning。
- 如果 acceptance_checks 为空，返回错误。

7. validate_task_verification.py

功能：
- 校验 task-verification-report.json。
- pass 时 failed_checks 必须为空。
- revise/block 时必须有 minimal_repair_instructions 或明确 block reason。
- 如果 should_trigger_direction_evaluation 为 true，必须有 new_findings。

8. status.py

功能：
- 读取 task directory。
- 打印：
  - current phase
  - current milestone
  - current task
  - last route decision
  - blocked issues
  - next recommended action

========================
六、Codex agent 配置要求
========================

在 .codex/config.toml 中设置：

[agents]
max_threads = 6
max_depth = 1

注意：
- max_depth 保持 1，防止 subagent 递归创建 subagent。
- reviewers 可以并行。
- task executor 可以按任务顺序执行；只有无依赖任务才允许并行。
- 不要让 executor 自己 spawn verifier。
- orchestration 由主 Codex session 根据 Skill 完成。

每个 .codex/agents/*.toml 必须包含：
- name
- description
- developer_instructions

权限建议：
- questioner：read-only
- researcher_proposer：read-only
- reviewers：read-only
- adjudicator：read-only
- proposal_summarizer：read-only
- planner：read-only
- direction_evaluator：read-only
- task_decomposer：read-only
- final_summarizer：read-only
- executor：workspace-write
- result_verifier：优先 read-only；如果运行测试需要写缓存，只允许写临时文件或测试输出，不允许修改实现代码。
